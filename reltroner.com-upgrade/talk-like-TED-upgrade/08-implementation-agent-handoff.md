# 08 — Deterministic Source-Implementation Handoff for a Future Agent

> Status: DESIGN HANDOFF — NO SOURCE CODE MODIFICATION WAS PERFORMED BY THIS DOCUMENTATION TASK.  
> Scope: six public pages in Reltroner/reltroner-studio and ONLY affected shared frontend components if independently justified.  
> Read preceding files before any source execution.

## 1. Mission

Refine reltroner.com according to the owner-approved **Emotional → Novel → Memorable** experience architecture integrated with Reltroner Studio's two value engines and WOS's usage-first mental-model learning. **Preserve existing correct behavior and minimize added code.**

The required outcome is an understandable, emotionally relevant, causally novel and memorable experience that routes users voluntarily to functioning creator, reader and archive resources. Do not implement decorative three-card constraints or invent unsupported learning claims.

## 2. Mandatory preflight

1. Identify exact repository/workspace and active branch. Ensure the owner-authorized working tree is protected. Never reset/clean untracked author work or assume old local paths.
2. Inspect current main/target HEAD and **all six** page sources plus the components they import. Compare against this folder's October 24 source snapshot; note drift.
3. Load binding Studio Master, latest website contracts/ADRs, security/cost/privacy rules and proposed Communication Framework and WOS candidate. Select newer *explicitly scoped* ratifications without erasing historic records.
4. Inspect current rendered site at mobile and desktop; record baseline, CTA destinations, existing notebook data behavior, navigation, provider status and assets only to the extent needed for the authorized patch.
5. Produce the smallest implementation file list and do not modify anything beyond approved UX scope. Existing source architecture is the default.

## 3. Execution order

**P0 — Message and information architecture**
- Home: keep the two pathways; prioritize concise identity, one meaningful proof and truthful CTAs.
- Creator: translate jargon into an understandable example; eliminate repeated explanations, not necessary mechanics.
- Reader: stakes before taxonomy, noncanon and published-content statuses explicit.
- Explore: preserve four curiosity intents and collections; make next relevant path visible.
- About: articulate Desire → Discovery → Continuing Practice with real evidence.
- Contact: low-pressure question and realistic asynchronous semantics; protect transport.

**P1 — Bounded experiential enhancements, only after P0 review**
- Where inspectably useful, add an optional creator reflection after the existing creative loop: what changed, why and what next question inherits it?
- Connect existing reader lens/scale interactions to one consistent hypothetical case without creating new canon.
- Add editorially verified causal links to Explore where existing content supports them.
- Keep motion restrained and optional; preserve current CDN resource semantics.
- Add only lightweight code, not a graph service, storage backend, account requirement or new provider.

**P2 — Validation and decision**
- Verify route, form, notebook, newsletter, navigator, images/media, accessibility, mobile and desktop regressions.
- Run comprehension and recall probes if owner has participants/approved measurement; otherwise label those outcome tests **NOT_RUN** rather than **PASS**.
- Record exact SHA, changed paths, tests, screenshots and known limitations.
- Request normal controlled release acceptance; do not equate a passing build with deployment.

## 4. Required non-negotiables

- Three cognitive anchors are messaging principles; not constraints on number of UI elements or course modules.
- Avoid new expenses, dependency inflation, cross-write to LMS, authentication, paid tools or privileged API exposure.
- Keep creative content/notes creator-controlled; no silent third-party model calls.
- Keep canon flags, source provenance and fiction/Earth distinctions.
- No unsupported courses, sales, sign-ups, live sessions, testimonials or social proof.
- Preserve current working provider and anti-abuse contracts, including Resend and contact transport.
- Do not alter deployed CDN resources unnecessarily; investigate broken assets using approved resource syncing rather than changing image intent.
- Existing navigation/reading rules must follow latest owner-approved ADR; no resurrection of obsolete rails, headers or /start routing unless confirmed binding in current scope.
- No automatic Git push/deploy without applicable release rules, documented effect scope and authorization.

## 5. Definition of done for a patch

A patch is acceptable only when:
- every changed section serves the correct route responsibility;
- the change has a documented before/after reason (problem → change → expected value);
- all linked CTAs are truthful and functional;
- one clear cognitive takeaway is offered *where appropriate*, while content depth remains discoverable;
- essential guest tasks and accessibility/performance/security/privacy remain intact;
- automated and manual evidence covers changed behavior;
- user-facing claims use correct epistemic status;
- the owner can inspect and decide whether the bounded implementation is accepted.

## 6. Fail-closed behavior

If sources, availability, design contract or provider economics cannot be verified, avoid irreversible edits or invented claims; preserve the existing behavior and document the narrow blocker. Failure to validate a cross-domain learning effect does not authorize claiming it succeeded. Failure to find a meaningful UX defect is not permission to invent a major feature.

## 7. Artifacts to return to owner after implementation

An efficient handoff contains: exact changed-file list, reason for each edit, preserved behaviors, tests executed with result, screenshots and viewports actually examined, source/preview/production SHAs and statuses, open issues, any copy requiring editorial ratification and rollback plan. Only label public deployment accepted after the appropriate release and runtime checks.
